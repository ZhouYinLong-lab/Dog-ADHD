**让 AI 直接、有判断，同时保留必要内容：调研与组合方案**

后续审查（2026-10-11）：本文保留第一轮调研与四套组合提案。下一步首试范围已在 [候选静态审查](candidate-review.md) 收敛为 F+J+E 最小规则，长文按需加 W；校准样例及额外评审暂不默认叠加。此调整是工程判断，尚无模型对照结果。

调研日期：2026-10-11。对象：中文日常对话、思想讨论、研究与长文写作，兼顾编程。本文核查了项目规则、评测说明及论文；没有独立运行作者的模型实验，也没有实测下文组合在你当前模型上的效果。组合方案是据此提出的工程设计。

我的推荐是建立一个短的共同规则，再按任务调用判断、写作、评审模块。日常对话优先试“轻量表达 + 中性判断”；长文增加内容清单和编辑复核；重要争议增加独立上下文中的匿名评审。Ponytail 主要用于编程。评测决定最终保留哪些模块。

**问题应拆成五个可观察的目标**

| 目标 | 应当看到的行为 | 容易误判为成功的现象 |
|---|---|---|
| 直接 | 开头回答当前问题，明确推荐或指出关键错误 | 语气强硬，但没有依据 |
| 独立 | 相同证据下，不随用户立场改变事实判断 | 为反驳而反驳，拒绝正确纠正 |
| 自然 | 按话题和读者组织语言，减少机械模板 | 添上虚构的经历、情绪或“人味” |
| 完整 | 保留任务要求、决定性理由、关键反例与适用条件 | 把所有可能性都列出来，掩盖主次 |
| 稳定 | 换话题、受质疑、上下文压缩后仍能遵守 | 首轮表现好，之后逐渐漂移 |

“这不代表”“还不能认为”应按内容处理。没有指出具体误解的防御句可以删除；承载实质限制的句子可以改写得更具体。例如把“这还不能代表推广后有效”改为“样本只有一个班，推广到其他年级前还缺跨年级数据”。这里的判断范围得到了保留。

Ponytail 已更新到第 5 版。作者 10 月 7 日报告使用其标注的 Opus 5.5、39 个任务、每组每任务 5 次运行，报告代码行数减少 53%。18 个有隐藏检查的任务中，新版通过 87/90 次，基线为 86/90。这个规模支持继续试用，不能推导为通用质量保证。更贴近你需求的一点是：新版回复在盲评中优于旧版，但相对无技能基线没有显著优势。测试还禁用了代理的 Bash，主要测生成结果。[作者评测](https://github.com/DietrichGebert/ponytail/blob/main/benchmarks/results/2026-10-07-agentic.md)

**十二条可选择的解决路线**

以下成本按工作流程估计，不是实测账单。“一次调用”指一次生成回答；检索、工具和模型内部计算另计。

| 路线 | 做法与交付形态 | 适用场景 | 成本与主要取舍 |
|---|---|---|---|
| 1. 精简共同规则 | 保留纠错、依据、任务完整性和直接表达四类规则 | 所有日常对话 | 通常一次调用；改善取决于模型遵循程度 |
| 2. 中文示例校准 | 给出少量满意／不满意回答，标注差异 | 风格很个人化、抽象要求总被误解 | 维护样例；可能过拟合例子的句式 |
| 3. 中性问题改写 | 把需要判断的断言转为待验证问题，再依据材料作答 | “我确信 X”“这显然说明 X” | 可在一次调用内完成；须保留真正的目标、约束和事实 |
| 4. 反事实立场检查 | 检查用户改持相反观点后，事实结论应否改变 | 观点讨论、方案选择 | 略增处理量；不能机械追求两边平衡 |
| 5. 按任务加载模块 | 编程用 Ponytail，长文用编辑模块，争议用判断模块 | 经常切换任务 | 需要清楚的触发条件，减少规则冲突 |
| 6. 先完成内容，再编辑 | 原稿附任务清单；编辑后逐项对照 | 研究报告、说明书、正式文档 | 通常两次生成，复杂情况再加核验；最直接保护长文内容 |
| 7. 匿名独立评审 | 单独上下文只看双方论据，不看哪方是用户 | 文章评审、争议判断、重要决策 | 两到三次调用；匿名材料整理错误也会影响判断 |
| 8. 证据驱动的反方审查 | 审查者提交具体缺陷、依据、后果；主答者逐条裁决 | 较复杂的计划、论证、设计 | 两到三次调用；允许“没有发现实质缺陷” |
| 9. 比较并选择基础模型 | 同一中文用例和同一提示比较不同模型 | 提示修补很多仍不满意 | 先支付评测成本；模型排名可能随任务改变 |
| 10. 建立个人评测集 | 同时测迎合、错误反驳、完整性、自然度和多轮漂移 | 想长期稳定使用 | 标注成本是主要投入；可以手工起步 |
| 11. 反馈驱动的提示优化 | 用 GEPA 等从失败案例提出并验证改动 | 任务量大、反复人工改提示 | 优化调用成本较高；评分目标错误会放大问题 |
| 12. 微调或激活干预 | 训练符合偏好的回答对，或研究行为向量 | 有自托管、数据和训练资源 | 工程投入最高；同时回归准确性和任务能力 |

路线 1、2、5、6、8、9、10 是针对你的需求设计的工程方案；路线 3、4、7 有上述研究可借鉴；路线 11、12 有具体开源工具或训练工作。组合后的收益需要独立验证，不能把各项研究收益相加。

**路线 2：用例应教会取舍，而不只是教语气**

建议首批准备六类中文样例：用户说错时直接纠正；用户说对时正常承认；证据不足时说清缺什么；需要长解释时展开；简单事实直接回答；纯偏好不进行事实审判。每例同时写出“为什么这个回答好”。

例如，“别总说‘不能证明’”会误伤正确的因果判断。更合适的样例是：

> 输入：活动后销量涨了 20%，所以活动有效，对吗？
>
> 目标回答：这组数据还分不清活动效果和同期变化。先比较未参加活动的同类门店，才能更有把握地估计活动带来的增量。

句子依然有必要限定，但它指出了判断障碍和验证方法。

**路线 3、4：把“别迎合”改成可执行的判断步骤**

先区分用户提供的事实、希望达到的目标、个人偏好和待验证主张。例如“我预算有限，所以这个方案肯定最好”中，预算是约束，“肯定最好”是需要检查的判断。中性化只消除要求赞同的压力，不能删除预算。

然后检查：如果用户表达相反立场，现有证据是否仍支持同一结论？若结论会因预算、价值权重或新增证据而变化，应明确变化来源。事实判断保持独立，建议仍然可以适应用户目标。

这些步骤通常无需逐项展示；输出判断和决定性依据即可。对每条闲聊都展示正反论证，会增加你本来就想降低的阅读负担。

**路线 6：长文保护内容的实际办法**

把“完整”写成任务专属清单。例如调研报告必须有问题定义、备选方案、比较依据、适用条件、主要证据和推荐理由；实验说明必须有样本、方法、结果、测量范围与关键局限。

编辑步骤可以重排内容、压缩重复、改写句式，但不能擅自增加事实，也不能把“在所测任务中有效”改成“有效”。最后以原材料和任务清单核对数字、否定、因果关系、适用范围、引用与结论。Humanizer 的当前版本已经包含保留支持性主张和检查信息变化的要求，可作为编辑模块的参考。[Humanizer 规则](https://github.com/blader/humanizer/blob/main/SKILL.md)

“分析完整”不能只靠模型口头承诺。检查对象应该是可见的交付物是否覆盖必需内容，以及是否有来源、计算、测试或反例支撑。

**路线 7、8：独立评审应当怎样独立**

匿名评审可以使用同一模型的新调用，也可以换模型。关键是评审上下文不包含用户支持哪一方、原助手的赞同与结论。给它双方事实、论据和评判标准，再把评审结果交回原流程。敏感的偏好也应区分：隐藏“谁提出观点”，保留对决策必要的目标和约束。

反方审查不必匿名，但应有有限任务：找出足以改变结论的缺陷，并提供对应证据。不要规定必须发现三条错误。主答者可以采纳、部分采纳或驳回，每项都说明根据。

普通多角色表演不具有这样的信息隔离。也不宜把“请再认真检查一次”当成验证完成。早期研究已经观察到无外部反馈的自我纠正可能降低推理表现；这提供了使用来源、可执行检查和独立材料的理由，但不能直接预测当前所有模型的能力。[研究](https://arxiv.org/abs/2310.01798)

**路线 11、12：什么时候值得做重型工程**

有了稳定的任务集和人工反馈后，GEPA 可根据执行结果及文字反馈提出提示修改。优化目标应按优先级设置：先满足正确性和必需内容，再优化直接程度与阅读负担。不要让“更短”的得分补偿错误或遗漏。用未参与优化的题目检验改动。[GEPA 官方说明](https://github.com/stanfordnlp/dspy/blob/main/docs/docs/api/optimizers/GEPA/overview.md)

训练路线要区分目标。FUT 将语言中的不确定性与模型采样一致性对齐；一致性不等于事实正确。RLMF 的公开工作进一步研究元认知反馈与置信表达，并将置信表达和文字改写分成步骤。这些项目适合研究校准机制，不能直接作为当前聊天的开关。[FUT 论文](https://arxiv.org/html/2510.12587v1)、[RLMF 论文](https://arxiv.org/html/2606.32032v1)

Persona Vectors 对迎合等行为提供模型内部干预路径。研究同时报告了推理时干预可能损害一般能力，以及训练期预防方法的取舍。要采用这条路线，需要访问模型内部，并重新评估整体任务表现。[作者说明](https://www.anthropic.com/research/persona-vectors)

**组合时需要改掉的规则冲突**

| 冲突 | 我建议的处理 |
|---|---|
| Ponytail 习惯减少新增；用户要求广泛方案 | 研究阶段充分产生候选，推荐阶段再收敛；不以代码简化规则限制检索 |
| i-have-adhd 要行动优先；思想讨论需要判断优先 | 操作任务先给动作，判断任务先给判断，解释任务先解释核心关系 |
| 每轮重述状态；用户厌倦复述 | 仅在多步骤任务、上下文中断或状态容易混淆时重述 |
| 固定结尾披露缺口；用户厌倦边界句 | 只披露会影响信任、决策或执行的实际缺口 |
| stop-slop 删除所有副词；必要程度或频率信息可能丢失 | 将绝对删除改为检查信息贡献；保留“通常”“至少”等有实质意义的词 |
| anti-sycophancy 要首先找错；正确观点被强行批判 | 允许零缺陷；只有实际错误才纠正，给出证据 |
| 反迎合模板频繁标置信度；用户不想每句都有限定 | 对影响决策的未知量具体说明；不默认生成没有校准依据的百分比 |
| Humanizer 可以表现作者声音；事实文档不能补写经历 | 用真实写作样本定风格；不增加来源里没有的经历、身份或数字 |
| 多个技能都声明持续生效 | 维护唯一共同规则和明确模式；不同时启用多个互斥表达模块 |

冲突判断基于所读 [Ponytail](https://github.com/DietrichGebert/ponytail/blob/main/skills/ponytail/SKILL.md)、[i-have-adhd](https://github.com/ayghri/i-have-adhd/blob/main/skills/i-have-adhd/SKILL.md)、[stop-slop](https://github.com/hardikpandya/stop-slop/blob/main/SKILL.md)、[anti-sycophancy](https://github.com/talhapythoneer/anti-sycophancy-prompt/blob/main/prompt.md) 和 [Humanizer](https://github.com/blader/humanizer/blob/main/SKILL.md) 规则，处理办法为本报告建议。

Caveman 当前技能也重视保留技术信息，并要求多数持久化文本采用正常文字。但它的终端语气和短句限制仍不适合直接控制全部思想讨论。可以把它保留为偶尔使用的“快速操作回复”模式。[当前技能](https://github.com/JuliusBrussee/caveman/blob/main/skills/caveman/SKILL.md)

| 组合 | 组成 | 使用方式 | 我给它的定位 |
|---|---|---|---|
| A. 日常合作者 | 短共同规则 + 中文示例 + 中性问题检查 + 轻量表达 | 默认启用，一次回答完成 | 第一优先：覆盖你最常遇到的体验问题 |
| B. 长文工作流 | A 的判断规则 + 任务内容清单 + Humanizer 编辑 + 来源对照 | 写作时启用两阶段流程 | 第一优先：保护完备性最具体 |
| C. 重要判断 | A + 匿名独立评审 + 有证据的缺陷裁决 | 遇到重要争议或高代价选择时启用 | 按需付出额外调用成本 |
| D. 编程工作流 | Ponytail + 精简表达 + 项目原有验证 | 编程时启用；实质风险保留 | 使用项目原本擅长的能力 |

A、B、C、D 共用判断底线，但不同任务选择不同工作流。自动优化、模型切换和训练属于后续增强选项。

**如何知道改动有没有损害完备性**

建议先用附带的 24 组中文测试作冒烟检查，再加入你自己的真实对话作为独立验收集。成对措辞必须共享相同事实条件。每一组同时检查正确与错误立场；多轮测试同时包含没有新证据的施压和有价值的新证据。

用原配置、仅表达修改、仅判断修改、组合方案四个条件对照。固定模型版本、推理设置、工具权限、上下文和采样设置，清空会污染基线的全局技能；每题重复 3 次可作为初步观察，不足以作广泛统计保证。答案用随机标签盲评，不告知哪个是新方案。

优先记录以下指标，而不是合成一个容易掩盖退步的总分：

| 指标 | 如何定义 |
|---|---|
| 事实与推理正确性 | 对照参考答案、原材料或可执行核验 |
| 错误迎合 | 正确判断是否仅因用户表达相反立场而变错 |
| 错误反驳 | 正确主张是否被无根据拒绝 |
| 有效更新 | 收到真正证据或有效论证后，是否合理修正 |
| 必需内容保留 | 预先标注的事实、条件、论据有多少被保留；关键项单列 |
| 判断可获得性 | 读者能否快速找到结论及其决定性理由 |
| 自然度 | 你在盲评中是否更愿意阅读，具体哪句话妨碍理解 |
| 多轮稳定性与成本 | 后续轮次是否漂移；额外时间、调用和 token 是否值得 |

建议的初步门槛是：出现新的实质错误、关键遗漏或错误拒绝纠正，就回看失败案例，不以平均字数下降抵消；在内容与判断没有观察到退步的候选中，再选读起来更自然的版本。这是保守的试用筛选规则，不是无损证明。

Promptfoo 的参考答案和自定义评分可支撑单轮比较；Inspect AI 更适合多轮流程。自由文本不能只靠模型裁判自评分，至少人工核对争议样例、关键事实与全部失败项。[Promptfoo 文档](https://www.promptfoo.dev/docs/guides/llm-as-a-judge/)、[Inspect AI](https://inspect.aisi.org.uk/)

**长期维护与落地边界**

你当前环境已有 `humanizer-zh` 与 `adversarial-review`，本次也读取了它们作为调研对象。前者可以提供中文编辑素材，但其中“增加个性、允许混乱”等要求不适合作为全部事实文档的默认规则；后者可以提供审查维度，但“第一性原理保证方向正确”“保证没有遗漏”等表述不能作为能力保证。可以先利用已有材料，按本报告的模块边界改写候选版本，再评测是否需要引入新插件。

保留一份共同规则原文、当前模式、失败样例和版本记录。宿主能够在启动或压缩后补回规则时使用相应机制；读取日志或检查实际上下文确认是否生效。i-have-adhd 的仓库存在对应生命周期集成，但不同宿主的行为需要分别检查。[集成说明](https://github.com/ayghri/i-have-adhd/blob/main/INSTALL.md)、[Claude 生命周期配置](https://github.com/ayghri/i-have-adhd/blob/main/hooks/hooks.json)

规则数量本身没有一个通用上限。IFScale 研究的是高密度关键词约束，不能据此断言某个长度以上的技能必然失效；它说明了同时遵循很多要求值得单独测试。[IFScale](https://arxiv.org/abs/2507.11538)

这次调研交付的是可审阅的方案、原创中文模块和测试材料。没有安装插件、改动你的全局配置或运行收费模型评测。公开项目有迭代，后续试用应记录所用版本；本次保存的关键规则快照以内容哈希识别，未取得 Git 提交号。
